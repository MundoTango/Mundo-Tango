2. Plan backend: tables + PlanTrackerService + GitHub webhook

This is the “Plan items + work log + GitHub connection” feature.

✅ What’s already done
	•	PlanTrackerService.ts exists in server/services/mrblue/.
	•	The methodology doc defines:
	•	Plan-related entities: planItems, planLinks, workLog.
	•	A GitHub webhook at server/routes/webhooks/github.ts that will eventually:
	•	Map PR/commit events → Plan/workLog entries.
	•	The doc explicitly calls out that Plan schema and routes are not fully implemented yet.

🧩 What’s next to do
	1.	DB schema
In shared/schema (or equivalent):
	•	Implement or finalize:
	•	planItems table:
	•	id, title, description, status, priority
	•	assigneeUserId, relatedUserId (e.g., the volunteer the work relates to)
	•	source (e.g. talent_match, ops, etc.)
	•	createdAt, updatedAt, dueAt
	•	planLinks table:
	•	id, planItemId
	•	type (e.g., github_pr, github_issue, doc, mrblue_session, etc.)
	•	url, externalId, metadata (JSON)
	•	createdAt
	•	workLog table:
	•	id, planItemId
	•	actorType (human | agent)
	•	actorId (user id or agent id)
	•	message (human-readable summary)
	•	rawData (JSON payloads, e.g. GitHub webhook bodies)
	•	createdAt
	•	Add necessary indexes (by assignerUserId, relatedUserId, status, createdAt).
	2.	Plan API routes
	•	Create server/routes/plan-routes.ts (as the doc mentions) with endpoints like:
	•	GET /api/plan/items – list items (with filters by volunteer, status).
	•	POST /api/plan/items – create a new plan item.
	•	PATCH /api/plan/items/:id – update status, assignee, description, etc.
	•	GET /api/plan/items/:id/work-log – fetch work log entries.
	•	POST /api/plan/items/:id/work-log – append manual human notes.
	•	Wire these to PlanTrackerService:
	•	Methods like:
	•	createPlanItem()
	•	updatePlanProgress()
	•	getUserPlanTasks()
	•	logWorkFromEvent() / generateWorkLogEntry()
	3.	GitHub webhook mapping
In server/routes/webhooks/github.ts:
	•	Parse GitHub events:
	•	pull_request, push, issue_comment, etc.
	•	Identify mapping to Plan:
	•	By branch name feature/talent-match-h2ac or AGENT_XX tags in PR titles.
	•	Or by magic comment / Plan-Item-Id: 123 in PR body.
	•	For each relevant event:
	•	Create or update planLinks entries for the PR/commit.
	•	Append workLog entries summarizing:
	•	Which plan item moved forward.
	•	What the agent / developer did.

🧪 Tests to run
	•	Unit tests for PlanTrackerService:
	•	Creating/updating items.
	•	Writing and reading workLog.
	•	Integration tests for /api/plan/...:
	•	CRUD operations with a fake user and a fake volunteer.
	•	Webhook tests:
	•	Simulated GitHub payloads posted to /api/webhooks/github.
	•	Confirm:
	•	Correct Plan item and workLog entries created.
	•	No duplicates on repeated webhook deliveries.

🎯 Definition of done
	•	Plan tables exist and are migrated.
	•	PlanTrackerService is fully wired and used by API routes.
	•	GitHub events reliably create/update Plan + workLog.
	•	A volunteer’s work can be traced from Plan → GitHub and vice-versa.

3. Talent Match ↔ Plan integration (roleProposer + Plan mapping)

This is where Talent Match events actually create Plan items and track progress.

✅ What’s already done
	•	The doc defines that we must:
	•	Extend Talent Match routes with roleProposer and Plan mapping.
	•	Integrate PlanTrackerService methods to:
	•	Assign a candidate to a Plan.
	•	Track progress as statuses change.
	•	Some of this may already be partially wired (the doc says: “inspect services (PlanTrackerService, roleProposer) and Talent Match routes to see which pieces are already wired”).

🧩 What’s next to do
	1.	Discovery
	•	Search for a roleProposer service / function:
	•	E.g. server/services/roleProposer.ts or similar.
	•	Check Talent Match routes:
	•	Where a candidate is accepted / rejected.
	•	Where clarifier answers are stored.
	2.	Plan mapping
	•	On submission or clear acceptance of a candidate:
	•	Call PlanTrackerService.createPlanItem with:
	•	relatedUserId = the candidate’s user id.
	•	title like “Onboard volunteer for [role]”.
	•	source = talent_match.
	•	On status changes (clarifier done, approved, rejected):
	•	Call PlanTrackerService.updatePlanProgress.
	•	On key events (clarifier completion, approval, rejection):
	•	Create workLog entries summarizing what changed.
	3.	wsNotificationService integration
	•	The doc mentions wsNotificationService:
	•	Hook Plan/Talent Match changes into notifications:
	•	Notify admins when a new candidate is ready.
	•	Notify volunteers when they get a new task or status change.

🧪 Tests to run
	•	Integration tests on Talent Match APIs:
	•	When a candidate is approved:
	•	A planItems record is created.
	•	At least one workLog entry exists.
	•	When clarifier status changes:
	•	workLog entry added with the correct summary.
	•	Notification tests:
	•	Confirm that calling the relevant Talent Match route triggers:
	•	A websocket / notification event with correct payload.

🎯 Definition of done
	•	Every Talent Match candidate has a Plan item tied to them.
	•	Status changes in Talent Match are reflected in Plan + workLog.
	•	Admins and volunteers see consistent state across:
	•	Talent Match, The Plan, and GitHub.

4. H2AC & Comet logging (Human ↔ Agent communication)

✅ What’s already done
	•	The doc clearly integrates H2AC:
	•	Comet agents must log:
	•	Intent, actions, and results for each Talent Match / Plan operation.
	•	These logs must be surfaced in human-facing dashboards for H2AC.
	•	Methodology pattern:
	•	Any system that maps human work ↔ agent work must:
	•	Use GitHub-first + Replit-for-verification.
	•	Log agent actions into something like workLog / H2AC fields.

🧩 What’s next to do
	1.	Decide the H2AC data model
	•	Option A: reuse workLog with:
	•	actorType = 'agent'.
	•	actorId = 'comet_xx' or similar.
	•	Option B: add a separate agentLog table and link to planItems.
	2.	Instrumentation points
	•	Anywhere a Comet / agent:
	•	Creates or updates a Plan item.
	•	Changes Talent Match statuses.
	•	Handles GitHub mappings.
	•	Wrap these operations in a helper function:
	•	logAgentAction({ actorId, planItemId, action, details }).
	3.	Expose H2AC to humans
	•	API:
	•	GET /api/plan/items/:id/h2ac or reuse work-log endpoint.
	•	UI:
	•	The admin pipeline and My Tasks page should show:
	•	Plain-language summaries of what agents did.
	•	Time stamps and links to the underlying PRs / commits.

🧪 Tests to run
	•	Unit tests:
	•	logAgentAction helper (or equivalent).
	•	Integration tests:
	•	Simulate an agent-driven Plan update:
	•	Verify actorType = 'agent' and proper message in workLog.
	•	Manual UI:
	•	Open the admin pipeline and a plan item:
	•	Confirm human-readable logs of agent behavior.

🎯 Definition of done
	•	Every agent-driven change in Talent Match / Plan is logged in a way humans can read.
	•	Admins can see:
	•	What the agent tried to do.
	•	Whether it succeeded or failed.
	•	Links to GitHub or relevant artifacts.
